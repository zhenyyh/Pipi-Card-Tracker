# 从游戏能拿到什么数据（完整版）

按「采集 → 事件 → 推导 → 不可得」四层整理。所有字段均来自实际代码，
不是推测。对应实现：`pct/gs_install.js`（采集）、`pct/tracker.py`（推导）。

数据通路：`jsclient.data.sData`（内存快照）+ `pomelo`（网络事件）
→ frida 注入读内存 → 写 `pct_state.json` → tracker 解析。

## 第一层：内存快照（直接读到的确定值）

来源：`jsclient.data.sData.tData`，由 `snapshot()` 每 600ms 或事件触发时采样。

### 1.1 牌桌全局

| 字段 | 含义 | 实测说明 |
|---|---|---|
| `me` | 我的 uid | 来自 `jsclient.data.pinfo.uid` |
| `tState` | 牌局状态 | **3=出牌 4=等人出牌 5=等响应（可吃碰胡）8=胡牌确认 6=结算 -1=平局** |
| `tableid` | 牌桌 id | 换桌必变 |
| `playNum` | 第几局 | 局号，用于作废旧 AI 结果 |
| `uids` | 座位 uid 数组 | 2 人局，下标 = 座位号 |
| `curPlayer` | 当前该谁出牌 | 座位号 |
| `zhuang` | 庄家座位号 | **判断「对家是否庄」的唯一依据** |
| `lastPut` | 最后打出的牌 | 牌值编码见下 |
| `lastPutPlayer` | 最后出牌的人 | ⚠️ 不可靠，对手出牌后有时仍显示为我 |
| `lastDrawPlayer` | 最后摸牌的人 | — |
| `cardNext` | 发牌指针（已摸走张数） | 与 `choupai` 一起算剩余 |
| `leftCards` | 剩牌 | ⚠️ **局中恒为空数组，只在结算时给** |
| `xingCard` | 醒牌 | ⚠️ **实测恒为 -1**，不可用 |
| `caiPaiArr` | 财牌数组 | 底牌兜底来源之一 |
| `sliceCard` | 是否切牌 | 布尔 |
| `firstSend` | 是否首发 | 布尔 |
| `winner` | 赢家 | -1 = 平局/未定 |

| `limitScore` | 封顶分 | 进 `roomRules` |
| `playType` | 玩法类型 | 进 `roomRules` |
| `visibleActions` | 本人可见操作按钮 | **由场景树扫描得出，见 1.3** |

牌值编码：小字 `1~10`，大字 `101~110`（`101`=大壹 … `110`=大拾）。

### 1.2 每个座位（`sData.players[uid]`）

| 字段 | 原始键 | 含义 |
|---|---|---|
| `put` | `mjput` | 该家打出的牌（有序） |
| `peng` | `mjpeng` | 碰（3 张一组） |
| `peng1` | `mjpeng1` | 偎（暗 3 张） |
| `gang0` | `mjgang0` | 提（明 4 张） |
| `gang1` | `mjgang1` | 跑（4 张） |
| `chi` | `mjchi` | 吃 / 绞（3 张一组，靠 `rules.classify` 区分） |
| `lie` | `mjlie` | 摆（单张亮出） |
| `hand` | `mjhand` | 手牌 —— **只有自己这一份是真的** |
| `handN` | — | 手牌张数 |
| `state` | `mjState` | 玩家状态 |
| `handKnown` | — | 该家 `mjhand` 是否真的是数组（区分「空手牌」与「没这个字段」） |
| `putKnown` | — | 同上，针对 `mjput` |
| `knownMeldFields` | — | 六个门子字段各自是否存在的细粒度标记 |
| `meldsKnown` | — | 六个门子字段是否全部完整 |

### 1.2b 实机枚举：两家的字段集**不一样**（2026-10-28）

在雷电 9 里 attach 后直接枚举 `sData.players[uid]`，两家各 22 / 29 个键，
**不是同一套**。这件事本身是结论：服务端只把「本人需要知道」的东西发给本人。

| 两边都有（16） | 只有本人那份（13） |
|---|---|
| `info` `onLine` `delRoom` `isNew` `winall` `winningStreak` | `mjhand` —— 手牌，服务端不下发给别人 |
| `mjpeng` `mjpeng1` `mjgang0` `mjgang1` `mjchi` `mjlie` `mjput` | `mjState` `waitLiuType` —— 本人的操作状态 |
| `mjputHand` `mjpengFrom` `mjptop` `mjwtop` | `mjpassChi` `mjpassPeng` —— **过张 / 过碰记录只有自己有** |
| `pengScore` `piaoType` `piaoSet` `sishou` **`needOneCard`** | `cannotPut` `eatFlag` `originEatFlag` `kingHuFlag` |

三条直接可用的：

1. **`onLine`** —— 对手掉线时牌局**停摆**，`tState` 一直卡在 3。
   实测踩到过（对手 `onLine=false`，界面看起来像「在等他出牌」，其实他不会动了）。
   记牌器该把它显出来，别让人以为是自己卡了。
2. **`mjpassChi` / `mjpassPeng` 只有本人有** —— 之前想拿过张约束对手，**方向错了**：
   这个字段记录的是「我过掉的牌」。广播里的 `MJPass.mjpassChi` 是桌面级累计列表，
   混着双方，不能当「他过了什么」。
3. **`needOneCard`** —— 对手那份里**有**，布尔值，含义待考证。
   若它等于「还差一张（听牌）」，那就是对手听牌状态的公开信号；
   若只是「发牌阶段少一张」，则无用。**必须靠实机逐手观察才能定**，
   工具：`python tools/watch_opp.py`（读常驻采集器落盘的 `pct_state.json`，
   纯文件读不碰 GL 线程，不会像反复 `evalString` 那样把游戏打到 ANR）。

`mjptop` / `mjwtop` 实机是空数组，暂按「没用」处理，不猜。

### 1.3 操作按钮可见性（场景树扫描）

`actionPanel()` 遍历 Cocos 场景树（上限 2500 节点，缓存 1 秒），
找名为 `eat` 的控制节点，检查其中的 `guo / hu / peng / chi0` 按钮
**及其所有祖先是否可见**，返回可见按钮名单。

这是「我现在能不能碰/吃/胡」的**唯一可靠证据**——比 `tState` 和
`lastPutPlayer` 都准（实测 `tState=4` 时按钮也会弹出）。

## 第二层：网络事件流

### 2.1 四个钩子入口

| 入口 | 说明 |
|---|---|
| `pomelo.emit` | 客户端事件派发 |
| `pomelo.notify` | 服务端主动推送（**底牌走这里**，只钩 emit 会全漏） |
| `pomelo.request` | 请求应答 |
| `pomelo.decode` | **最底层收包**，能看到「解出来但没往上派发」的字段 |
| `jsclient.netCallBack.*` | 游戏直接回调、绕过 pomelo 的路径（来源标 `s:'cb'`） |

### 2.2 监听的事件白名单（19 个）

```
MJPut  MJPeng  MJChi  MJGang  MJHu  MJPass  MJLao  MJWai
roundEnd  MJBeginHu  MJZhongJiang
mjhand  MJShow  MJShowPL  MJBegin  MJXing
MJBuxiaCard  MJYu  MJDi
```

非白名单事件**只记第一次出现**（用于发现新字段），不会刷爆队列。

### 2.3 事件记录结构

```json
{"s": "emit|notify|request|cb", "e": "事件名", "t": 时间戳ms, "q": 自增序号, "d": {字段}}
```

- `d` 内保留标量（字符串截断 80 字）和数组（最多 30 元素）
- 队列上限 **240 条**，超出丢弃最旧的
- `q` 是全局自增序号，用于去重（同一事件多路径到达时）

## 第三层：状态机推导（加工后的结论）

`pct/tracker.py` 把上面两层喂成可直接用的结论。

### 3.1 记牌器展示用的

| 数据 | 规则 |
|---|---|
| **底牌** `bottom` | 庄家第 21 张。**只在「对家是庄」时记**。优先级：开局第一条 `newCard` 的 `lastPut`（最准）→ 快照 `hand[20]` → `xingCard` → `caiPaiArr` |
| **首出** `first_put` | 对家为庄时，庄家打出的第一张 |
| **门子** `melds` | 每方含 `kind`（吃/碰/偎/提/跑/绞/摆）+ `cards` + `owner`（me/opp）+ `after`（该门子成型后打出的第一张）+ 时间戳 |
| **弃牌** `puts` | 双方打出的牌序列 |
| **回合流水** `timeline` | `{n: 序号, who: me/opp, act: put/peng_or_wei/chi_or_jiao/gang, card: 牌值}` |

门子**不合并**：手里 3 张又来同值要单独占一行（保留「中间那次成型」）。
最多显示 8 行（`MAX_ROWS`）。

### 3.2 给 AI 的派生量

| 字段 | 含义 |
|---|---|
| `deckLeft` | `max(0, 80 − choupai − cardNext)`，牌墩还剩几张 |
| `mySeat` | 我的座位号 |
| `responsePlayer` | 按钮可见即视为「该我响应」，否则 `None` |
| `availableActions` | 从可见按钮映射为 `peng / hu / pass / eat` |
| `roomRules` | `huziType / limitScore / playType` |

### 3.3 `analysis`（替模型算好，避免它自己数错）

| 字段 | 含义 |
|---|---|
| `meldCount` | 已成型门子数 |
| `needMelds` | `max(0, 7 − meldCount)`，还差几方到胡 |
| `pairs` | 对子（恰好 2 张的牌值列表） |
| `triples` | 坎（≥3 张的牌值列表） |
| `possibleRuns` | 手里已能凑成的一句话（一二三 / 二七十，大小字各一套） |
| `singleCount` | 孤张数量 |
| `seen` | 已露面的牌各几张，**上限夹到 4**（数据冲突保护） |

`seen` 的统计口径 = 我的手牌 + 双方门子 + 双方弃牌。
对手暗牌、墩里剩牌、抽走的 20 张都不在内，所以它是「**已确认已现**」，
不是「全部去向」。

### 3.4 读牌信号：对手思考时长 `oppThink`

**这是唯一能拿到的对手行为数据**，靠事件时间戳算出来：

```
newCard（每摸一张都发，带 Date.now() 时间戳）→ 对手 MJPut（出牌）
                                          ↑ 两者相减 = 纯思考时长
```

| 字段 | 含义 |
|---|---|
| `src` | `draw` = 从摸牌算起（纯思考，最准）；`gap` = 从上一张牌算起（含摸牌，兜底） |
| `last` | 最近一次耗时（秒） |
| `avg` | 平均耗时（秒） |
| `recent` | 最近 5 次（秒） |
| `n` | 样本数 |

口径与过滤：

- 区间 **200ms ~ 60s**，以下算 UI 动画/事件重发，以上算挂机掉线，都不计入
- 自己出牌时清空 `_draw_t`——否则对手随后碰/吃直接出牌（无摸牌过程）会被
  误算成「从我上次摸牌算起」的超长思考
- 换对手（`opp` uid 变化）时清空全部样本，旧主人的习惯不能用来判断新对手
- 样本 < 2 返回 `null`：单个样本分不出「他平时就快」还是「这次碰巧快」

**怎么用**：< 1s 秒出 → 多半是闲张；1~3s 正常取舍；> 3s 长考 → 可能在挑安全牌，
且**长考后打出的牌更可能是他确认过安全的**，不能因为「他打过」就认为我打也安全。

**红线**：它只能回答「他考虑过没有」，**不能反推他手里是什么牌**。
说「他想了 5 秒所以手里有成型的绞」就是编造——已写进提示词硬约束。

## 第三层补遗：抓到了但还没用上（2026-10-28 复核）

| `mjpassChi` | `MJPass`、`MJPut`、`MJChi` 负载 | **过张列表** —— 打出去没人吃碰胡的牌 | 已录制（`tracker.pass_chi`），口径未坐实，不进推断 |

| `tData.*` 全量 | 所有 `MJPeng/MJGang/MJChi` 负载 | 30+ 个房间参数 | 只取了 3 个，见下 |

### 5.1 `mjpassChi` —— 唯一的「过张」证据

一张牌打出去、没人要，它就进这个数组。语义上等于「这张对某一家没用」，
是**能直接削弱对手手牌假设的公开证据**，比思考时长硬。

★ 但口径没坐实：`round_v3` 里座位 0 的 `MJPut` 带回全局列表
`[10,1,103,103,4,7,9]`（含对手打过的 1/4/103），座位 1 的只回自己的
`[1,4,105]`。83 个样本里「等于自家累计」22 个、「等于双方累计」1 个、
都不是 60 个 —— 按座位存，但自己那份混进了被吃走的牌和对方的牌。

**裁决工具**：`python tools/probe_pass.py`。补 1~2 局带 `MJPut` 的实战流，
看计数往哪边倒。口径没定之前不要接进 AI。

★ **用它当「他没有这张」的否定约束，已被标签打掉。** 拿 4 局 fixture 对终局手牌：

```
round_draw   过张[110,1,10,6,108,102]          终局双方手牌交集 = 空
round_kan    过张[109,104,105,3,5,9,4,8]       交集 = [104, 3, 5, 4]
round_multi4 过张[109,104,105,3,5,9,4,8]       交集 = [109, 5, 9, 8]
round_v3     过张[10,1,103,103,4,7,9,104,7]    交集 = [1]
```

4 局里 3 局命中。原因很直白：**过掉的是「那一张」，不是「这个牌值」**——
同一个值有 4 张，他过后又摸到一张很正常。

所以过张只能做**弱证据**：某个值已经死掉 N 张 → 能等的张数变少。
**不能**推成「他手里没有这个值」，那是错的，标签直接证伪。

### 5.2 `tData` 里还有一半房间规则没读

已经进 `roomRules` 的只有 `huziType / limitScore / playType`。实际还有：

| 字段 | 含义 |
|---|---|
| `canEatHu` / `canEatMustHu` | 可吃胡 / **吃必胡**（实测 true，直接影响能不能放过张） |
| `isEatHuForce` | 强制吃胡 |
| `daNiao` / `daNiaoScore` | 扎鸟开关 / 鸟分（实测 true / 10） |
| `addScore` / `addScoreRule` / `addScoreNum` | 加分玩法 |
| `needAddCard` / `addCardNum` | 补牌 |
| `offScore` | 掉线扣分（实测 3） |
| `owner` | 房主 uid |
| `roundNum` / `roundAll` | 剩余局数 / 总局数 |
| `tableShareStatus.cardCanShow` | 能否亮牌 |
| `canDiHu` / `gangAllLie` / `showWei` / `qiduidaikan` | 地胡 / 提全亮 / 偎公开 / 七对带坎 |

`canEatMustHu=true` 这条最要紧：它意味着「能胡就必须胡」，AI 建议里
「先不胡等更大的」那种思路在这个房间是非法的。

### 5.3 反证：对手手牌在网络层就不存在

### ★ 更正（2026-10-28）：`roundEnd` 里有双方终局手牌

`roundEnd.players[uid].mjhand` 是**每一家的终局手牌**，输家的也有：

```
roundEnd.players = {
  "5513337": {"mjhand": [106,101,102,2,6,108,1,3,101,108,102], "winall": 70, ...},   ← 输家
  "5519304": {"mjhand": [2,109,8,2,8,108,107,108], "mjdesc": ["十红","自摸"], ...}    ← 赢家
}
```

这是游戏自己在结算面板上亮出来的东西，**不是破防拿到的暗牌**。
所以「局中看不到、结算一定给」—— 这句话比原来那句「服务端根本不下发」准确。

| 用途 | 说明 |
|---|---|
| **带标签样本** | 每打完一局自动多一条：中间状态 + 最终答案。`tools/harvest_rounds.py` 已能导出 |
| **枪毙错误假设** | 任何「他不可能有 X」的推论都能拿来对标签，见 5.1 的反例 |
| **算上下界** | 确定他有 ⊇ 终局手牌；可能有 ⊆ 终局手牌 ∪ 之后打出的 ∪ 之后成门子的 |

★ 注意 `roundEnd.tData.playNum` 比同局的 `mjhand` 事件**大 1**（实测 4 vs 3）。
拿局号当换局边界，会在结算那一刻把整局累计冲掉 —— 换局信号要用 `mjhand`（发牌）。

### ★ 再更正：结算那一刻 `sData` 里也能拿到，而且更好用（2026-10-28 实机）

实机第 10 局结算（`tState=6`）的快照里：

```
seat0 (我)      handN=15  handKnown=true   hand=[7,4,102,...]
seat1 (对手)    handN=17  handKnown=true   hand=[101,1,1,2,103,...]
leftCards      15 张 = [101,10,7,108,1,105,3,102,10,9,103,108,110,1,108]
cardNext=45  choupai=20 → 60-45=15 ✓ 完全对上
```

两条：

1. **`players[对手].mjhand` 局中为空、结算填满** —— 所以标签有两条通路：
   `roundEnd.players`（事件）和 `sData.players`（快照）。
   **优先用快照**：采集器的事件记录只保留标量和数组（数组截 30），
   `roundEnd.players` 是嵌套对象，**会被整个丢掉**，实机流里那一栏是空的。
2. **`leftCards` 结算给全量墩剩牌**（15 张）。以前只知道「张数」，现在知道「是哪 15 张」。

### 守恒对不上的那 1 张：已定位（2026-10-28）

第一次手算是 61：

```
我手 15 + 对手手 17 + 我门子 6 + 对手门子 3 + 双方弃牌 5 + 墩剩 15 = 61
```

**多出来的 1 张是 `lastPut=105`。** 那一局 `lastPutPlayer=1`、`winner=0`：
对手打出 105，赢家（本人）拿它胡了。牌进了赢家手牌，
但**出牌方的 `put` 不会把它移除** —— 于是它同时算进「赢家手牌」和「对手弃牌」，
数了两遍。

这条规则 README 的口径速查里早就写了（「弃牌堆要剪掉已易主那张」），
只是一直没落进代码。现在在 `Tracker.conservation()` 里，剪完正好 60。

### 守恒的边界清单（每一条都会让账「看起来像采集失败」）

| # | 边界 | 错法 | 判据 / 处理 |
|---|---|---|---|
| 1 | **池不是 80** | 差 20，误判成采集漏牌 | 二人房 `choupai=20` 抽走 → 池 = `80 - choupai` = 60 |
| 2 | **胡牌那张已易主** | **多 1 张** | `lastPut` 出现在赢家手牌里 ⇒ 从其他家 `put` 里剪掉一张。实测第 10 局 105、multi4 的 109 |
| 3 | 自摸 | 不该剪 | `lastPut` 是赢家自己摸的，不进任何人 `put` —— 剪了会变 -1。判据同上（不在别人 `put` 里就不会被选中） |
| 4 | **偎/提/跑 数组元素是「组」不是「张」** | 少 4 张 | `peng1` 一组 3 张、`gang0`/`gang1` 一组 4 张；`[109,107]` 是 6 张不是 2 张 |
| 5 | 吃 / 绞 | 少算 | `mjchi` 3 张一组，按 `len // 3` 拆 |
| 6 | 摆火 | 少算 | `mjlie` 一个元素 = 1 张 |
| 7 | **空手牌 ≠ 没读到** | 把「未知」当 0 张去凑 | `handKnown=True` + `hand=[]` 是真的 0 张（胡完全打进明牌）；`handKnown=False` 才是未知 |
| 8 | 局中对手 hand 不下发 | 算出 -15 之类的假缺口 | 记进 `unknown`，`ok=False`，**不拿 diff 下结论**。只有 `tState=6` 两家 hand 都有值才能算整账 |
| 9 | 旧房间 `cardNext` 可能超过池 | 墩剩出负数 | clamp 到 0 |
| 10 | 吃/碰/绞 也可能已易主 | 不明 | **已定案：不会**。第 2 局（荒庄，座 0 三组吃、座 1 十四张明牌）差 0 且一次不用剪 —— 吃/碰时会从出牌方弃牌堆移除，**只有胡牌那张不会**。候选仍只报不剪（同值 4 张，光看值分不清是不是同一张） |
| 11 | **荒庄**（`winner=-1`） | 容易误以为要剪 | `cardNext=60` 抽干、双方各留 7 张、`leftCards=[]`；`winner<0` 时不做任何剪切，实测差 0 |

实现：`Tracker.conservation()` 返回可对账的诊断（`pool / seats / clipped / candidates /
sum / diff / ok / unknown`），不是一句 True/False。回归：`python tests/test_conservation.py`（9 项）。

> **唯一还没闭合的**：`round_kan` 差 +1 且找不到可剪的牌。它剪不掉，而「吃/碰也会重复计数」
> 这条刚被第 2 局证伪 —— 所以它不可能是公式问题。README 早已记该局
> 「live 与事件张数本身对不齐」（旧房间 `tableid=812760` 的残留），**别再改公式去凑**。

## 一句话总结

**能确定看到**：自己 20 张手牌、双方所有公开门子、双方所有弃牌、
每张牌的先后顺序、牌墩还剩几张、庄家是谁、当前该谁动、我现在能做什么操作。

**确定看不到（局中）**：对手手里的牌、墩里躺着的牌、抽走的 20 张。
这三样是服务端刻意不给的，任何「推测」都只会污染判断。

**但结算一定给**：`roundEnd.players[uid].mjhand` 双方都有。别拿它当「当场能看牌」，
拿它当**每局白送的标签**，用来校准「局中怎么猜」。

**唯一能确定的对手信息 = 他打过什么 + 他亮出过什么门子 + 他终局剩什么。**
